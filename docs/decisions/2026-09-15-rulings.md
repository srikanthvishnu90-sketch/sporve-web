# Rulings — 2026-09-15

Five decisions the owner made after the v2 spec set landed. Binding; agents
implement them and do not re-litigate them. Recorded here because each one
closed a question that was blocking work, and three of them create debt or
delete something — those need a reason on the record, not just an instruction.

---

## R1 — `providers` stays the organisation root. New tables carry `provider_id`.

There is no `organizations` table and there will not be one this cycle. The v2
master spec's tenancy convention ("every table carries `organization_id`") is
satisfied by naming the *column* consistently and pointing it at
`public.providers(id)`.

**The debt, stated plainly.** The org root is called `providers` — a name from
the coach-marketplace product, where a "provider" was an individual coach
selling sessions. In the club-ops product it means an *organisation*: a club, an
academy, a league. Every new engineer will read `provider_id` on `event_series`
and think it means a coach. Two identifiers for the same concept already coexist
in the live schema: `organization_members.organization_id` references
`providers(id)`, while 27 other child tables use `provider_id`.

**Why we are taking it anyway.** A rename touches every table, every RLS policy,
every SECURITY DEFINER function body, every edge function and the whole SPA, and
it buys no customer-visible behaviour. It is cheap today and gets more expensive
with each table that FKs it — but "cheap today" still means a multi-hour rewrite
of the exact surfaces (RLS, Stripe, minors' data) where a silent mistake is most
expensive, during the one window when scheduling has to ship.

**How the debt is paid, when it is paid.** As a single mechanical migration:
rename `providers` to `organizations`, keep a `providers` view for one release,
rename `provider_id` columns to `organization_id`, then rewrite the function and
policy bodies. Not before G9. Not while any spec in the 11–18 set is open.

**Until then, for anyone reading the schema:** `providers` = organisation.
`provider_id` = organisation id. `organization_members.organization_id` is the
same thing under the other name. New tables use `provider_id` for consistency
with the 27, not with the 1.

## R2 — `GATES.md` is canonical. It is now the v2 G1–G10 ladder. G3 SUPPLY is deleted.

Four numbering schemes existed simultaneously (GATES.md's four gates,
CONTEXT.md's two business gates, the CLAUDE.md/AGENTS.md pointer that ratified
the first while declaring it superseded, and the v2 spec's ten). Agents read
these files and act on them, so this was not cosmetic.

GATES.md is rewritten to the v2 ladder and is the only file that defines gate
numbers. Every other document cites gates by number *from it*. AGENTS.md and
CLAUDE.md drop their own enumeration; their "no new AI tool until G4" becomes
G6 (WRITES ARE SAFE) — the same gate under the new number.

**G3 SUPPLY is deleted, and the reason is recorded in GATES.md itself:** it
measured catalogue liquidity for a two-sided marketplace. The product sells to
organisations that arrive with their own coaches and roster; there is no supply
side to fill. The real question it asked — *does a real organisation run on
this?* — is now G9, which is strictly harder.

**Note on D14.** The 2026-09-15 decisions say neither agent edits GATES.md. This
rewrite is an explicit owner instruction that overrides that line for this
change only. D14 otherwise stands.

## R3 — Flutter retirement deletes the client only.

Delete in `sporve-app`: `lib/`, `ios/`, `android/`, `web/`, `test/`,
`pubspec.yaml`, `pubspec.lock`, `analysis_options.yaml`, and build artefacts.
**Keep `supabase/`** — it holds ~44 edge-function directories and 103
migrations, including the stripe-webhook patched in sporve-app#47.

**Flagged, not acted on: the duplicate edge functions.** sporve-web and
sporve-app both carry `supabase/functions/`, with overlapping names and at least
one file (stripe-webhook/index.ts) that had to be patched twice. Which repo is
the canonical home, and whether the other's copy is deleted or made a pointer,
is a **separate task**. Nothing in this cycle touches it.

## R4 — The narrow launch cuts migration (spec 17). Registration (spec 14) stays.

The v2 README proposed the opposite. The owner's ruling: registration is how an
organisation's *money* starts, and it is the first thing a club does in the
buying window (Nov–Jan, before winter/spring registration opens). An importer is
how a club leaves a competitor — valuable, but it is a sales demo, and for the
first ten orgs it can be done by hand.

Consequence: **G10 (migration under an hour) is explicitly not a launch gate.**
G9 is launch. The first ten migrations are performed manually by the owner, and
what those ten teach is the specification for the importer built next cycle.
Spec 17 is not cancelled; it is scheduled after G9.

## R5 — A cancellation always drafts. No auto-send, no exception.

Spec 12.4 targets "under 15 seconds from a coach's phone on a field to a
parent's SMS". That target stands — but it is measured **approval to delivery**,
not approval removal. The draft-first invariant is not negotiable for the one
message class most likely to be sent in a panic, from a field, in the rain.

**What this means for the build.** The optimisation target is *two taps from the
home screen to a sent cancellation*, with the message already written:

1. The cancellation draft must exist **before** the coach reaches for the phone —
   generated the moment `status` flips to cancelled, not on approval.
2. It must be the first thing in the agent rail and the destination of the
   push/SMS deep link, not something to be found.
3. Approve is one tap, and the 8-second hold with Undo stays — it costs nothing
   against a 15-second budget and it is the only thing standing between a
   mis-tap and 60 families being told practice is off.

Spec 12.4's DoD is amended to measure approve to delivery receipt, to assert
zero sends without an approval, and to assert a tap count from a cold
home-screen launch.

`cancel_event(p_event, p_reason, p_notify)` as shipped in #432 already behaves
this way: it sets status and reason, the trigger drafts one notice per family,
and it returns a receipt naming how many were drafted. Nothing sends. No
auto_send_cancellations flag was built, and none should be.
